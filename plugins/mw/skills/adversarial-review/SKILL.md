# Adversarial review

A step that touches a costly path, and every stone, merges only after a reviewer that did not write the code has tried to refute it (AGENTS.md "Working Units and Sessions"). A step that touches no costly path merges on green CI, and the stone review reads it with the rest of the stone (ruled by the owner on 2026-10-12, the review-cut stone). The reviewer is a separate `claude -p` process started by `${CLAUDE_PLUGIN_ROOT}/tools/review_pr.py`. It starts with an empty conversation and sees the diff, the stone's plan or exit test, the invariant list, CI's suite result for the reviewed commit and the repository. It never sees the author's reasoning. It reports blocking findings and unresearched choices, and on a step round it also lists the findings about the records under `## Records`.

## Run it

```powershell
python "${CLAUDE_PLUGIN_ROOT}/tools/review_pr.py" <pr-number> --post
```

Run it on every step and on the stone's pull request to `main`; the tool decides whether a review is due.

- **Which pull requests get a review.** The tool reads every file the pull request changes. A step that touches no path in the costly-path list of the repository's `.claude/mw.json` gets no review: the tool prints `no review: the step touches no costly path`, posts nothing and exits 0. `--force-review` reviews such a step anyway, on the owner's request. `documents/process/model-choice.md` lists the paths and says how the list changes.
- **What the reviewer reads.** The tool takes the diff from git, from the merge base with the pull request's base branch, because GitHub refuses a pull-request diff over 300 files. Upstream files under `third_party/<library>/` arrive as a count per library, not as text.
- **What the reviewer runs.** Nothing of the full suite. CI has run it under the sanitizers on the reviewed commit and posted its `mw-tests` comment, which the tool waits for, up to thirty minutes, and puts in the prompt; the merge tool refuses a merge without a green run on that commit; and the suite wrapper refuses an unfiltered run from the reviewer, which runs with `MW_REVIEWER=1`. A finding that needs a run of the reviewer's own, such as a new test that must be seen to fail, gets a filtered run over the test files it names, which takes the machine's suite slot for seconds. When CI has not posted for the commit when the reviewer starts, the review says so under Verified, and the merge tool's CI wait covers it (the owner's request of 2026-10-21, the engine's issue 686). `--no-wait-ci` skips the wait.
- **What the reviewer measures against.** For a step, the tool appends the body of the stone's open pull request to `main`, which holds the approved plan. After the body it appends the plan's tables: each comment on that pull request that opens with `<!-- mw-plan-tables -->`, in order. `--stone <id>` adds the stone's section of the phase plan, under `### Stone N`, `### N —` or `### The N stone`. A step cut before the stone's first step wrote that section lacks it at its head; the tool then reads it from the stone branch, or from the step below's branch, and the prompt names the ref. `--context <file>` appends any other text, such as the list of open sibling steps.
- **A diff past one prompt.** From 0.1.13 on, the tool splits a diff over the data file's `review.slice_bytes`, 800,000 bytes by default, into slices by path, in git's order (the engine's issue 906). It runs one reviewer per slice, all at once, each in its own detached worktree at the head, with the same model, effort and turns. It merges their reviews into one comment, and that comment counts as one round. A lone file past the budget forms a slice of its own: the slice holds the file's stat line and the command that reads the file in the worktree, in place of its text. A slice whose reviewer fails, or answers without its round's headings, runs once more, and a second failure exits 2 and posts nothing. A fix check's diff slices by the same rule. The tool prints the diff's size, its file count and its slice count before the CI wait. A diff that needs more than `review.max_slices` slices, 8 by default, exits 2 at once, before the wait: split the review by hand, or raise the key in the data file. `--slice-bytes N` sets the budget for one run.
- **One round per step.** A step gets one round, over its whole diff. A second run on a step exits 2 with a line saying so, and only the owner grants another round, with `--extra-round owner`. The stone review rereads every step's fixes over the whole stone diff.
- **The stone review's rounds.** The tool's comment records the reviewed commit and the round. Round 1 reviews the whole diff. A rerun after fix commits is a fix check: the reviewer sees the earlier findings and only the commits since, and answers whether each finding is fixed and whether the fixes broke something. A clean merge of the pull request's base after round 1 is left out of the fix check: its tree is git's own merge of its two parents, so it brings only commits reviewed through their own pull requests. When only such merges follow a clean round, the tool runs no reviewer, prints `nothing to review`, and exits 0. A rebase, or a merge of the base that is not clean (a conflict resolved by hand, an edit folded in), gets a full review, because the diff since the reviewed commit would then carry code the stone never wrote. `--full` forces a full review, for a large rework or on the owner's request.
- **The stone review's fix round.** Every blocking round gets one fix round. A round after a blocking round that still blocks, because an earlier finding was not fixed or the fix broke something, exits 3. The round after an exit 3 refuses to start without `--extra-round agent` or `--extra-round owner`. `agent` is the author's own grant: the tool allows it once per pull request and only while no extra round, the owner's included, has run, and runs it only with `--post`. `owner`, or the bare flag, needs the owner's word. The tool's comment records the first extra round and its grantor. Give the flag after the pull-request number, which it would otherwise take as its value. A clean round spends nothing.
- **The model.** The kind of change picks it: a pull request into `main` is a stone review, and a step that touches a costly path gets its one round, both on `claude-fable-5-2` at high effort; a step reviewed under `--force-review`, and a later round the owner grants a step, run on `claude-opus-5-5` at high effort. The tool names full model ids, because a `claude` command older than 2.1.280 sends the alias `opus` to `claude-opus-5`; with the full id it fails loudly instead. `--model` and `--effort` override the choice when the owner or the stone's approved plan asks.
- **In the background, stacked.** A round takes minutes. Run the tool in the background and start the next step on a branch cut from this step's branch. When the next step's code is ready and its quick check passes, open its pull request against this step's branch, never as a draft, and run the tool on it while this step is still in review: CI runs on a pull request into a step branch, its size counts only its lines over the step below, and its reviewer reads the stone's plan. Keep at most three step pull requests open at once. Once the step below has merged, `${CLAUDE_PLUGIN_ROOT}/tools/merge_step.py` merges the step above as exit 0 says below. It retargets the pull request to `stone/<slug>`, computes the merge of `origin/stone/<slug>` into the step's head with `git merge-tree`, pushes that merge, and waits for CI on the new head. No new round runs: CI on the new head is the check that the two steps still fit. The tool refuses a stacked step whose step below has not merged.

  One exception skips the push and the wait (ruled by the owner on 2026-10-14). When the merge's tree equals the head's tree, the two share one merge base, and a green run on that head wrote the result summary, the tool merges at once at that head. The stone branch then brings nothing the head lacks, so the tree CI judged is the tree that merges. A run the retarget started on that head may still be going; the tool leaves it. The tool applies the same test to a step that is not stacked. Such a step whose tree differs now gets the merge pushed and a CI wait too, because otherwise CI never judges it beside the siblings that merged meanwhile.

  A stacked branch never merges the stone branch in before the step below merges. CI would then measure the step against the old base and count other steps' lines as its own, as Stone 12's step 5c's red size check showed.

  After any merge of the stone branch into a step, CI's run on the merged head judges it, even when git reports no conflict, and the author runs no local suite over it, because CI's run is a step's one full gate. Two siblings that both change one struct break an aggregate initialiser with no conflict (Stone 12's step 4a after step 3). Two siblings that both raise one log-baseline count merge clean to a wrong count (Stone 12's step 9b, measured at 51). CI's run on the merged head builds and runs the suite over such a merge, and the merge tool merges only on a green run there.

  A conflict in that merge stops the tool with exit 2 before any push or CI wait, naming the files, for a step stacked or not. The author resolves it by hand, pushes, and runs the tool again. A finding in the step below that changes what the step above builds on is fixed in the step below. When the step below is closed unmerged, retarget the step above to the stone branch and rebase it there.

  Retarget every step stacked on a merged step before deleting the merged step's branch, because GitHub closes a pull request whose base branch is deleted and cannot reopen it. On Stone 11, pull request 284 closed this way and pull request 287 replaced it. A stone keeps its step branches until its close.

## Forward references inside one stone

A stone's steps often cite files or rulings that a sibling step lands: a findings doc names the decisions doc that records its rulings, and the decisions doc names the findings doc. At step level such a citation is a forward reference, not a defect, when the sibling step is open on the same stone branch or named in the stone's plan. Say so in the pull request body, so the reviewer does not report the path as missing. The stone's own review over the whole diff is where every reference must resolve.

## Act on the findings

1. **Triage the labels.** The reviewer's label is a proposal. A finding blocks only when it meets the blocking rule in the tool's prompt, and the prompt holds one rule per kind of round (ruled by the owner on 2026-11-10):
   - A stone round, on the stone's pull request to `main` and its fix checks, blocks when the step's claim or the exit test is not met, an invariant is broken, two tracked docs contradict each other or a doc states a false fact, a named path, heading or command does not exist, or a tool can lose data or leak a secret.
   - A step round, on a pull request into a stone or a step branch, costly or forced, blocks when the step's own claim or the stone's exit test is not met, a claim of verification that no test carries included; when a repository invariant is broken; when a path or a command that a tool, a skill or a rule file names does not exist; or when a tool can lose data or leak a secret.

   A step round's reply carries a fourth heading, `## Records`, for a finding about the records: a contradiction between two docs, a false statement in a doc, a wrong citation, a missing heading or path a doc names, a comment's wording. A Records bullet stops no merge, and the tool's exit code and blocking count never read it. The coordinator copies each Records bullet onto the `Records:` line of the step's brief (item 5), and the stone's closing step fixes them together (`mw:close-stone` skill, item 8). A step round's `## Verified` holds at most three bullets of one sentence each, or one line when Blocking holds `- none`. A stone round and a fix check keep their longer form. A finding the reviewer labelled blocking that only meets the Records list moves to that line too. Code that later departs from a closed stone's dated record is no finding. A blocking label on anything else gets a reply on the pull request that names the rule it fails, and the finding is dropped. Triage a finding in the round where it first appears; one left blocking there cannot be ruled off the blocking rule at a later exit 3.
2. **An unresearched choice** (the reviewer's `## Unresearched choices` heading, item 7 of its prompt) stops the merge: research the one question with the `mw:prior-art` skill, post the question and its answer on the stone's pull request, then ask the owner with a recommendation (`documents/process/agent-rulings.md`, pre-ruling 8). A bullet from item 8 of the prompt, a rebuilt part with no row in the stone's port-triage record, is not such a choice and does not stop: it is a part the record missed, which gets a dated comment on the stone's pull request and a new row in the record, or a replan when it changes the stone's scope (`mw:port-triage` skill, "When it runs").
3. **The exit code** says what comes next:
   - 0: write the step's brief to a file in the scratchpad (item 5), then run `python "${CLAUDE_PLUGIN_ROOT}/tools/merge_step.py" <pr> --brief <file>` in the background (ruled by the owner on 2026-10-13). The tool waits for CI on the head commit, merges with a merge commit only when the newest green run on that head built or said that no code path changed and no later run there is red, and then posts the brief. A run on an older head never counts, and a GitHub error reads as unknown and polls. Its header lists each check. It reads every conclusion before it merges, because a merge chained behind a wait in one command ran on a red run too (Stone 5, step 9). It never deletes a branch. Its exit code says what comes next:
     - 0: merged, and the brief is on the stone's pull request.
     - 1: a run on the head is red. Fix the step, or follow pre-ruling 11 of `documents/process/agent-rulings.md` when the cause lies outside it, and run the tool again.
     - 2: it stopped before the merge, and its last line says why. A run queued past ten minutes calls for `documents/process/ci-runner.md`, "When a run stays queued". A conflict, which the tool finds before any wait and reports with the files, calls for a merge by hand. A pull request whose only run checked the size calls for a pushed commit. A brief whose `Ambiguities` item runs over 600 bytes calls for one sentence per ambiguity.
     - 3: merged, but the brief did not post; post it by hand.

     After adding the `size-exempt` label, push a commit, an empty one if nothing else is due (`git commit --allow-empty`), to start a fresh run. `gh run rerun` replays the original event and never sees the label, and an edit to the body starts no run the merge tool accepts;
   - 1 on a step: fix each blocking finding with a commit on the step branch, or answer it with a written rebuttal on the pull request. Post a ruling in the form `documents/process/agent-rulings.md` gives that names the fix commit or the rebuttal for each finding (pre-ruling 1), then merge as exit 0 says, with no new round. When no fix fits inside the step, stop and ask the owner. A fix that changes what the pull request's body describes edits the body too;
   - 1 on the stone's pull request to `main`: fix it with commits on the stone branch and rerun, which runs the fix check (`mw:close-stone` skill, item 9);
   - 3, on the stone's pull request only: the fix round still blocks, on an unfixed finding or on a defect the fix brought in. Rule once, by the plan's pre-ruling 2: post the ruling comment on the pull request, then act on it. "One more round" reruns the tool with `--post --extra-round agent`. "Stop", or an exit 3 after the author's round, asks the owner, who rules the finding non-blocking, grants `--extra-round owner`, or takes the stone back;
   - 2: a tool error, or a round that must not start, such as a step's second round; the message says which. Rerun a failed round at most twice, then stop (pre-ruling 3).
4. **The stone's pull request to `main`** gets the review over the whole stone diff before it merges, every step included. Its fixes land as commits on the stone branch, and the next round is the fix check over them (`mw:close-stone` skill, item 9).
5. **The brief.** Write the step's brief in the form `documents/process/agent-rulings.md` gives. Its `Records:` line carries the round's Records bullets, or `none`. `${CLAUDE_PLUGIN_ROOT}/tools/merge_step.py` posts it on the stone's pull request as a new comment after the merge and prints it. Give the owner the same text.

## Do not

- Do not review your own diff with a subagent and call it the adversarial review. A subagent inherits the author's context.
- Do not merge over a blocking finding that nothing has closed. On a step, a fix commit or a rebuttal named in a ruling closes it; on the stone's pull request, a fix check that confirms the fix, or the owner's word on the thread.
- Do not pass `--full` to widen a fix check you dislike, or `--extra-round owner` (or the bare flag) or `--force-review` without the owner's word.
- Do not ask the reviewer about style. The lint owns style, and the prompt forbids it.
